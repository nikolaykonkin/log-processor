# Log Processor — многопоточный обработчик логов веб-сервера

## Описание

Программа читает CSV-файл с логами веб-сервера, параллельно обрабатывает записи с помощью пула воркеров, считает статистику по всем запросам, отдельно выделяет ошибки (статус-коды 4xx и 5xx) и выводит результат в консоль: общее число запросов, число ошибок, среднее время ответа, топ IP-адресов и список записей с ошибками.

## Стек

- Go 1.21+
- Только стандартная библиотека, внешних зависимостей нет
- Горутины и каналы
- Паттерны: pipeline, worker pool, fan-out (tee)
- `context` для отмены и graceful shutdown
- `sync.Mutex` и `sync.WaitGroup`

## Запуск

```bash
# Клонирование (или распакуйте архив)
cd log-processor

# Запуск с тестовыми данными
go run main.go processor.go testdata/logs.csv

# Запуск с детектором гонок
go run -race main.go processor.go testdata/logs.csv

# Запуск тестов
go test -v -race ./...
```

## Формат входных данных

CSV с заголовком и шестью полями:

```
timestamp,ip,method,url,status,response_time
2024-01-15 10:30:00,192.168.1.100,GET,/api/users,200,150
```

Строки, которые не удалось разобрать, пропускаются, а причина пишется в лог. Остальные записи обрабатываются как обычно.

## Архитектура pipeline

```
                                    +--> filter (status >= 400) --> collect errors
read --> process (3 workers) --> tee
                                    +--> aggregate (all entries) --> Statistics
```

1. **read** (`readLogs`) читает CSV построчно и отправляет записи в канал. Ошибки разбора уходят в отдельный канал ошибок.
2. **process** (`processLogs`) — пул из 3 воркеров, которые параллельно забирают записи из общего канала.
3. **tee** (`tee`) раздваивает поток: каждая запись попадает и в статистику, и в фильтр.
4. **filter** (`filterLogs`) пропускает только записи со статусом >= 400.
5. **aggregate** (`calculateStats`) считает статистику по всем записям: `TotalRequests` включает и успешные запросы, `ErrorCount` — только ошибки.

Сборка pipeline находится в `runPipeline` (`main.go`), поэтому интеграционный тест проходит через ту же проводку каналов, что и боевой запуск.

## Реализовано

- Pipeline read → process → filter → aggregate с раздвоением потока через tee
- Worker pool (3 воркера)
- `context` с отменой, прокинутый через все стадии
- Обработка сигналов ОС (SIGINT, SIGTERM) с корректным завершением
- Корректное закрытие каналов и полный дренаж канала ошибок
- Проверка на гонки: `go test -race`
- Unit-тесты стадий и интеграционный тест всего pipeline

## Работа с фидбеком преподавателя

Проект сдан и зачтен. Перед публикацией закрыты два замечания.

**1. `TotalRequests` считался неверно.**
Фильтр по статусу стоял перед расчетом статистики, поэтому `TotalRequests` совпадал с `ErrorCount`. Теперь после `processLogs` поток раздваивается через `tee`: статистика получает все записи, фильтр — только ошибки. Отфильтрованные записи собираются в отдельной горутине, иначе фильтр блокировался бы на записи в канал. Регрессия покрыта тестами `TestTee`, `TestCalculateStats_CountsAllEntries` и `TestPipeline_TotalRequestsCountsAllEntries`.

**2. Канал ошибок читался не до конца.**
Одиночный `select` с `default` терял часть ошибок, а при заполнении буфера канала `readLogs` мог заблокироваться на отправке. Теперь канал ошибок читается отдельной горутиной до закрытия, а `runPipeline` дожидается ее через `sync.WaitGroup`. Регрессия покрыта тестом `TestReadLogs_DrainsErrCh`.

Дополнительно: `calculateStats` упрощен до обычного цикла без лишней горутины, а среднее время ответа вынесено в метод `Statistics.AverageRespTime`.
